# replica 主备集群运维手册

> 适用环境：`10.18.1.27`（主）/ `10.18.1.28`（备），VIP `10.18.1.30/24`，控制机 `10.18.1.33`
> 脚本目录：`/home/sder/ha/replica/scripts`；完整部署说明见 [`../DEPLOY.md`](../DEPLOY.md)
> 本文所有命令默认在控制机 `10.18.1.33` 的 `/home/sder/ha/replica` 下执行。

---

## 1. 集群速览

### 1.1 节点与组件

| 项目 | 10.18.1.27 | 10.18.1.28 |
|---|---|---|
| keepalived | priority 150，初始 MASTER | priority 100，BACKUP |
| VIP | 持有 `10.18.1.30/24` | 不持有 |
| MySQL | 主库（可写） | 从库（只读，复制指向 VIP） |
| Redis | 主 | 从（指向 VIP:6379） |
| etcd | etcd1（2379/2380） | etcd2（2379/2380） |
| etcdvip | 仅主端运行（23790/23800） | 不运行 |

- VRRP：`virtual_router_id 251`，unicast（不依赖组播），`state BACKUP + nopreempt`
- 健康检查：`chk_mysql_ha`，interval 5s、fall 3、rise 2
- 容器：`restart: unless-stopped`，`network_mode: host`
- 重建方式：`RESTORE_MODE=clone`（默认，克隆约 30–40s；失败自动回退 mysqldump）

### 1.2 自动行为（重要）

| 场景 | 自动动作 | 耗时 |
|---|---|---|
| 主端 MySQL 不可用 / 只读 | 健康检查返回失败 → keepalived 进入 FAULT → 释放 VIP | 约 15s（5s × fall 3） |
| 备端接管 VIP | notify_master：排空 relay log、`RESET SLAVE ALL`、置可写、Redis 提升、启动 etcdvip | 约 4s（clone 集群） |
| 备端未持有 VIP | keepalived 检查永远返回 0，不会误进 FAULT | — |
| 备端复制异常 | 先轻量修复（重新指向 VIP + `START SLAVE`），15s 一次、最多 3 次；仍失败则 clone 全量重建 | 修复秒级；重建 30–40s |
| 节点成为 BACKUP | notify_backup：置只读、`RESET SLAVE ALL`、`CHANGE MASTER TO VIP`、`START SLAVE`、Redis `SLAVEOF VIP`、停止 etcdvip | 秒级 |

**关键点：`notify_master` / `notify_backup` 只在 keepalived 状态切换的那一次执行。** 如果切换发生时 MySQL 是停的，提升动作失败后不会自动补跑，需要手工执行一次 `replica-runner.sh master`（见 §5.1）。

### 1.3 相关路径

| 内容 | 路径 |
|---|---|
| 健康检查 / notify 脚本 | `/home/sder/ha/replica/scripts/` |
| keepalived 入口（root 所有） | `/etc/keepalived/replica-runner.sh` |
| 过渡日志 | `/home/sder/ha/replica/logs/keepalived-wrapper.log` |
| keepalived 系统日志 | `journalctl -u keepalived` |
| 运行态标记 | `/var/run/replica_*`，`/home/sder/ha/replica/.restoring` |
| 部署日志 | `/tmp/replica-deploy-<时间戳>/deploy.log` |
| 清理日志 | `/tmp/replica-cleanup-<时间戳>/cleanup.log` |

## 2. 一键部署（全新环境）

```bash
cd /home/sder/ha/replica
./scripts/deploy_cluster.sh \
  --node1 10.18.1.27 --node2 10.18.1.28 \
  --vip-list "10.18.1.30/24" \
  --fresh --yes
```

- `--fresh --yes`：**会清空**两台 `data/{mysql,redis,etcd1,etcd2}`，不可恢复。
- 流程：预检 → 清理/建目录 → 同步代码并渲染每节点配置 → etcd bootstrap → 主库 MySQL/Redis → VIP → 备库接入复制 → 备库 Redis/keepalived → 11 项验收。
- 耗时约 5 分钟（首次 MySQL 初始化占大头）。
- 失败时自动收集诊断到 `/tmp/replica-deploy-<时间戳>/diag-<节点>.log`。

前置条件：

- 控制机可免密 ssh 到两台节点，节点上 `sder` 可直接 docker、`sudo -n` 可用；
- 两台节点已有 `/home/sder/ha/replica` 与所需镜像；
- 两台之间已配置 `sder` 免密 ssh（从库重建依赖）；
- 节点上 `keepalived` 已安装且 `chrony` 时间同步正常。

## 3. 更新部署（保留数据）

> ⚠️ 不要直接把仓库里的 `docker-compose.yaml` / `scripts/base.sh` 覆盖到节点：
> 部署脚本会按节点渲染这两个文件（`.28` 的 `server-id=28`、`ETCD_NAME=etcd2`、`data/etcd2`）。
> 覆盖后 `.28` 会带着 `.27` 的身份启动。

### 3.1 只更新脚本 / 文档（不停服务）

```bash
for h in 10.18.1.27 10.18.1.28; do
  rsync -az --exclude 'data/' --exclude 'logs/' --exclude '.git/' --exclude '*.log' \
        --exclude 'docker-compose.yaml' --exclude 'scripts/base.sh' \
        /home/sder/ha/replica/ sder@$h:/home/sder/ha/replica/
  ssh sder@$h 'chmod +x /home/sder/ha/replica/scripts/*.sh'
done
```

- `check_*` / `notify_*` / `restore_*` 脚本**立即生效**，不需要重启 keepalived（下一次 5s 检查或下一次状态切换就会用新脚本）。
- 若 `replica-runner.sh` 本身有变更，需要重新安装到 root 目录：

```bash
for h in 10.18.1.27 10.18.1.28; do
  ssh sder@$h 'sudo -n install -o root -g root -m 755 \
    /home/sder/ha/replica/scripts/replica-runner.sh /etc/keepalived/replica-runner.sh'
done
```

- 若 `base.sh` 有变更，单独同步并确认渲染行没被改坏：

```bash
for h in 10.18.1.27 10.18.1.28; do
  rsync -az /home/sder/ha/replica/scripts/base.sh sder@$h:/home/sder/ha/replica/scripts/base.sh
  ssh sder@$h 'cd /home/sder/ha/replica && sed -E -i \
    -e "s#^IFACE=.*#IFACE=\"ens3\"#" \
    -e "s#^VIPS=\(.*\)#VIPS=(\"10.18.1.30/24\")#" \
    -e "s#^NODE1=.*#NODE1=\"10.18.1.27\"#" \
    -e "s#^NODE2=.*#NODE2=\"10.18.1.28\"#" \
    scripts/base.sh && bash -n scripts/base.sh && grep -nE "^VIPS=|^MYSQL_VIP=" scripts/base.sh'
done
```

### 3.2 更新 compose / MySQL 参数

compose 改动通常伴随 MySQL 容器重建（几秒不可用）。健康的滚动顺序：

```bash
# 1) 备节点先更新并重建（不影响 VIP）
rsync -az /home/sder/ha/replica/docker-compose.yaml sder@10.18.1.28:/home/sder/ha/replica/
ssh sder@10.18.1.28 'cd /home/sder/ha/replica && \
  sed -E -i \
    -e "s#^([[:space:]]*- --server-id=)[0-9]+#\128#" \
    -e "s#^([[:space:]]*- ETCD_NAME=)etcd[0-9]+[[:space:]]*\$#\1etcd2#" \
    -e "s#^([[:space:]]*- ETCD_ADVERTISE_CLIENT_URLS=http://)[0-9.]+:2379[[:space:]]*\$#\110.18.1.28:2379#" \
    -e "s#^([[:space:]]*- ETCD_INITIAL_ADVERTISE_PEER_URLS=http://)[0-9.]+:2380[[:space:]]*\$#\110.18.1.28:2380#" \
    -e "s#^([[:space:]]*- \./data/)etcd[0-9]+(:/etcd-data)[[:space:]]*\$#\1etcd2\2#" \
    docker-compose.yaml && \
  docker compose config | grep -E "server-id|ETCD_NAME"'
ssh sder@10.18.1.28 'cd /home/sder/ha/replica && docker compose up -d etcd mysql redis'

# 2) 计划内切换，让 VIP 先离开 .27（见 §5.5）
ssh sder@10.18.1.27 'sudo -n systemctl stop keepalived'

# 3) 原主节点更新并重建
rsync -az /home/sder/ha/replica/docker-compose.yaml sder@10.18.1.27:/home/sder/ha/replica/
ssh sder@10.18.1.27 'cd /home/sder/ha/replica && docker compose config | grep -E "server-id|ETCD_NAME"'
ssh sder@10.18.1.27 'cd /home/sder/ha/replica && docker compose up -d etcd mysql redis'

# 4) 恢复 .27 的 keepalived（BACKUP），需要时再切回（§5.5）
ssh sder@10.18.1.27 'sudo -n systemctl start keepalived'
```

校验渲染结果（必须）：

- `.27`：`server-id=27`、`ETCD_NAME: etcd1`、`data/etcd1`
- `.28`：`server-id=28`、`ETCD_NAME: etcd2`、`data/etcd2`

### 3.3 更新 keepalived 配置

```bash
ssh sder@$h 'sudo -n keepalived -t -f /etc/keepalived/keepalived.conf'
```

- 在**备节点**重启 keepalived 无影响。
- 在**主节点**重启 keepalived 会释放 VIP，备节点接管；由于 `nopreempt`，VIP 不会自动回到原主。
  需要保持原主时，先停备节点的 keepalived，再重启主节点的 keepalived。
- `replica-runner.sh` 路径或脚本属主变化时，keepalived 会报 `insecure` 并禁用 track script。

### 3.4 全量重装

```bash
./scripts/cleanup_cluster.sh --node1 10.18.1.27 --node2 10.18.1.28 --yes
./scripts/deploy_cluster.sh --node1 10.18.1.27 --node2 10.18.1.28 \
  --vip-list "10.18.1.30/24" --fresh --yes
```

## 5. 场景处置

### 5.1 两台 MySQL 都停了，但 keepalived 没停

**会发生什么**：主端健康检查连续失败 3 次（约 15s）后释放 VIP；备端接管 VIP 进入 MASTER，但 `notify_master` 因 MySQL 不在而提升失败。最终状态是“VIP 在备端、MySQL 全停”。之后 MySQL 被拉起时不会重新触发提升，需要手工补一次。

```bash
# 1) 确认 VIP 归属
for h in 10.18.1.27 10.18.1.28; do
  echo -n "$h: "; ssh sder@$h 'ip -o -4 addr show dev ens3 | grep 10.18.1.30 || echo 无'
done

# 2) 两台只起 etcd/mysql/redis（不要起 etcdvip，它只应由主端启动）
for h in 10.18.1.27 10.18.1.28; do
  ssh sder@$h 'cd /home/sder/ha/replica && docker compose up -d etcd mysql redis'
done

# 3) 等两台 MySQL 就绪
for h in 10.18.1.27 10.18.1.28; do
  until ssh sder@$h 'docker exec -e MYSQL_PWD="s<9!Own1z4" mysql mysql -uroot -N -B -e "SELECT 1"' >/dev/null 2>&1; do
    sleep 2
  done
  echo "$h MySQL ready"
done

# 4) 在持有 VIP 的节点补一次提升（示例为 .28；按实际 VIP 归属替换）
ssh sder@10.18.1.28 'sudo -n /etc/keepalived/replica-runner.sh master'

# 5) 另一台补一次降级/建链（健康检查通常会自动完成）
ssh sder@10.18.1.27 'sudo -n /etc/keepalived/replica-runner.sh backup'
```

如果两台都没有 VIP（keepalived 处于 FAULT），按 §5.2 的顺序启动。

### 5.2 两台 MySQL 都停了，keepalived 也已停 —— 受控启动

关键原则：**先定主，再启动；不要两台一起拉起 keepalived。**

```bash
# 0) 如 keepalived 还在跑，两台先停掉，避免启动过程中自动倒换/误触发重建
ssh sder@10.18.1.27 'sudo -n systemctl stop keepalived'
ssh sder@10.18.1.28 'sudo -n systemctl stop keepalived'

# 1) 两台启动 etcd（quorum 需要 2/3）
for h in 10.18.1.27 10.18.1.28; do
  ssh sder@$h 'cd /home/sder/ha/replica && docker compose up -d etcd'
done
sleep 5
ssh sder@10.18.1.27 'docker exec etcd etcdctl --command-timeout=5s \
  --endpoints=http://10.18.1.27:2379,http://10.18.1.28:2379 endpoint health'

# 2) 主节点（默认 .27；若 VIP 原本在 .28 则对调 27/28）启动 MySQL
ssh sder@10.18.1.27 'cd /home/sder/ha/replica && docker compose up -d mysql'
until ssh sder@10.18.1.27 'docker exec -e MYSQL_PWD="s<9!Own1z4" mysql mysql -uroot -N -B -e "SELECT 1"' >/dev/null 2>&1; do sleep 2; done

# 3) 主节点 Redis
ssh sder@10.18.1.27 'cd /home/sder/ha/replica && docker compose up -d redis'

# 4) 主节点 keepalived：拿 VIP，执行 notify_master
ssh sder@10.18.1.27 'sudo -n systemctl start keepalived'
sleep 8
ssh sder@10.18.1.27 'ip -o -4 addr show dev ens3 | grep 10.18.1.30'

# 5) 备节点 MySQL + Redis
ssh sder@10.18.1.28 'cd /home/sder/ha/replica && docker compose up -d mysql redis'

# 6) 备节点 keepalived：进入 BACKUP，自动建链
ssh sder@10.18.1.28 'sudo -n systemctl start keepalived'
```

启动前先确认“谁的数据更全”（见 §6.2）；如果 `.28` 的 GTID 是超集，应让 `.28` 先起 keepalived。

### 5.3 只有主库 MySQL 故障（备库正常）

- 自动：约 15s 后 VIP 漂到备库，备库被提升为主，业务恢复（clone 集群提升约 4s）。
- 原主库修好后 MySQL 会自动启动（`restart: unless-stopped`），健康检查把它配成 VIP 的从库；
  若未建链：`ssh sder@10.18.1.27 'sudo -n /etc/keepalived/replica-runner.sh backup'`。
- 需要切回原主（§5.5）前，先确认原主的 GTID 没有超出当前主库（§6.2），否则超出的那截不会自动补到新主。

### 5.4 备库复制异常 / 手动重建

**自动处置**：健康检查发现 `IO/SQL != Yes` 或没有复制关系时，先每 15s 一次轻量修复（重新指向 VIP + `START SLAVE`），最多 3 次；仍失败则触发 clone 全量重建（距上次重建至少 120s）。

观察过程：

```bash
ssh sder@10.18.1.28 'tail -f /home/sder/ha/replica/logs/keepalived-wrapper.log'
```

**手动重建备库**（必须在备节点执行，且本机不能持有 VIP）：

```bash
# 1) 清掉可能残留的重建进程
ssh sder@10.18.1.28 'sudo -n pkill -f restore_mysql_slave.sh || true'

# 2) 停 MySQL，把数据目录/日志交给 sder（脚本以 sder 身份运行，需 ssh 到 VIP）
ssh sder@10.18.1.28 'docker stop mysql || true'
ssh sder@10.18.1.28 'sudo -n chown -R sder:sder /home/sder/ha/replica/data/mysql /home/sder/ha/replica/logs'

# 3) 重建（默认 clone；需要逻辑导出时用 RESTORE_MODE=dump）
ssh sder@10.18.1.28 'timeout 1800 /home/sder/ha/replica/scripts/restore_mysql_slave.sh'

# 4) 验证
ssh sder@10.18.1.28 'docker exec -e MYSQL_PWD="s<9!Own1z4" mysql mysql -uroot -e "SHOW SLAVE STATUS\G" \
  | grep -E "Master_Host|Slave_IO_Running:|Slave_SQL_Running:|Seconds_Behind_Master"'
```

### 5.5 计划内主备切换 / 切回

**主 → 备（.27 → .28）**：

```bash
# 停主节点 keepalived：notify_stop 会把 .27 降级为从库，VIP 释放
ssh sder@10.18.1.27 'sudo -n systemctl stop keepalived'
sleep 8
# 确认 VIP 已到 .28、.28 已提升
ssh sder@10.18.1.28 'ip -o -4 addr show dev ens3 | grep 10.18.1.30'
ssh sder@10.18.1.28 'docker exec -e MYSQL_PWD="s<9!Own1z4" mysql mysql -uroot -N -B \
  -e "SELECT @@read_only,@@super_read_only"'
```

**切回（.28 → .27）**：

```bash
# 若 .27 的 keepalived 还停着，先启动它（此时为 BACKUP，不会抢 VIP）
ssh sder@10.18.1.27 'sudo -n systemctl start keepalived'

# 停 .28 的 keepalived，VIP 自动回到 .27
ssh sder@10.18.1.28 'sudo -n systemctl stop keepalived'
sleep 8
ssh sder@10.18.1.28 'sudo -n systemctl start keepalived'   # 重新作为 BACKUP 接入

# 验证
ssh sder@10.18.1.27 'ip -o -4 addr show dev ens3 | grep 10.18.1.30'
ssh sder@10.18.1.28 'docker exec -e MYSQL_PWD="s<9!Own1z4" mysql mysql -uroot -e "SHOW SLAVE STATUS\G" | grep Running'
```

> `nopreempt`：VIP 一旦去了备机，不会因为原主机优先级高就自动回来，必须按上面的步骤主动切。

### 5.6 整机重启（掉电 / 重启 OS）

- 容器 `restart: unless-stopped`、keepalived 已 `enable`，开机会自动拉起，一般不需要手工干预。
- **例外**：重启前如果手工 `docker stop` 过容器，`unless-stopped` 不会自动启动它们，需要 `docker compose up -d`。
- 开机顺序不可控时，可能短暂出现“VIP 已到 .28、.27 的 MySQL 还在启动”的过渡状态；等 1–2 分钟再巡检：

```bash
for h in 10.18.1.27 10.18.1.28; do
  echo "===== $h ====="
  ssh sder@$h 'uptime -p; systemctl is-active keepalived; \
    docker ps --format "{{.Names}}: {{.Status}}" | grep -E "^(mysql|redis|etcd|etcdvip):"'
done
cd /home/sder/ha/replica && ./scripts/check_cluster_status.sh
```

若 2 分钟后仍异常，按 §5.1 / §5.2 处理。

### 5.7 全量清理

```bash
cd /home/sder/ha/replica
./scripts/cleanup_cluster.sh --node1 10.18.1.27 --node2 10.18.1.28 --yes
```

清空容器与 `data/{mysql,redis,etcd1,etcd2}`，恢复部署前 keepalived 配置；镜像和仓库保留。
**不可恢复**，执行前确认没有需要保留的数据。

### 5.8 运行态残留文件

| 文件 | 含义 | 处理 |
|---|---|---|
| `/var/run/replica_promoting` | 提升进行中（120s 内有效） | 一般等它过期；确认无提升进程可删 |
| `/var/run/replica_demoting` | 降级进行中（120s 内有效） | 同上 |
| `/var/run/replica_repair_count` / `_last` | 轻量修复次数/时间 | 数据级错误时自动清；手工清可重置重试 |
| `/var/run/replica_restore_last` | 上次重建时间 | 与 `RESTORE_INTERVAL=120` 配合 |
| `/var/run/replica_restore.lock` | 重建互斥锁（flock） | **不要删**；进程退出自动释放 |
| `/home/sder/ha/replica/.restoring` | 重建进行中标记（内容为 PID） | 仅当 PID 已不存在时删除 |

```bash
# 只在确认没有重建/提升在进行时执行
pgrep -af 'restore_mysql_slave|mysql_notify_master' || true
ssh sder@10.18.1.28 'sudo -n rm -f /var/run/replica_promoting /var/run/replica_demoting \
  /var/run/replica_repair_count /var/run/replica_repair_last'
ssh sder@10.18.1.28 'sudo -n rm -f /home/sder/ha/replica/.restoring'
```

## 6. 数据丢失边界（重要）

### 6.1 各组件会丢什么

| 数据 | 最坏情况 | 原因 |
|---|---|---|
| 停服期间的新写入 | **不存在** | 两台 MySQL 都停了，写不进去；失败的请求在应用侧，与恢复方式无关 |
| 停止前已提交的事务 | **不丢** | InnoDB 默认 `innodb_flush_log_at_trx_commit=1`，返回成功即已刷盘 |
| 停止前已提交、但备库还没收到的事务 | **可能丢** | 只存在于原主库；若恢复时让落后的备库当主，原主库这段会被覆盖 |
| Redis | 最多约 1 秒 | `appendfsync everysec`；正常 `docker stop` 不丢，掉电/`kill -9` 最多 1 秒 |
| etcd | 不丢 | Raft 已提交数据持久化；etcdvip 是 learner，重建成员不影响集群数据 |

结论：**“最多丢停止至今的数据”不准确**。停止期间没有 MySQL 数据可丢；真正要防的是“让落后的节点当了主”。选对主，落后的节点会自动追上，一条不丢。

### 6.2 恢复前先比对 GTID，决定谁当主

```bash
g27=$(ssh sder@10.18.1.27 'docker exec -e MYSQL_PWD="s<9!Own1z4" mysql mysql -uroot -N -B \
  -e "SELECT REPLACE(@@gtid_executed, CHAR(10), \"\")"')
g28=$(ssh sder@10.18.1.28 'docker exec -e MYSQL_PWD="s<9!Own1z4" mysql mysql -uroot -N -B \
  -e "SELECT REPLACE(@@gtid_executed, CHAR(10), \"\")"')

# .27 是否包含 .28 的全部事务（1 = 包含）
printf "SELECT GTID_SUBSET('%s', @@gtid_executed);\n" "$g28" \
  | ssh sder@10.18.1.27 'docker exec -i -e MYSQL_PWD="s<9!Own1z4" mysql mysql -uroot -N -B'

# .28 是否包含 .27 的全部事务（1 = 包含）
printf "SELECT GTID_SUBSET('%s', @@gtid_executed);\n" "$g27" \
  | ssh sder@10.18.1.28 'docker exec -i -e MYSQL_PWD="s<9!Own1z4" mysql mysql -uroot -N -B'
```

判定：

| 结果 | 含义 | 做法 |
|---|---|---|
| .27 包含 .28 | .27 数据更全 | 让 .27 当主，先起 .27 的 keepalived |
| .28 包含 .27 | .28 数据更全 | 让 .28 当主，先起 .28 的 keepalived |
| 两边互相包含 | 数据一致（正常停机场景） | 谁当主都可以 |
| 互不包含 | 停服期间有应用绕过 VIP 直写某一台 | **停止自动恢复**，人工确认取舍后再启动 |

> 互不包含时不要直接起 keepalived：备节点健康检查可能触发 clone 全量重建，把其中一台的“独有事务”覆盖掉。
